# Issue Triage

## Disclaimer

Every comment or issue posted to the issue tracker during triage MUST begin with:

```
> *This was generated by AI during triage.*
```

No exceptions.

## Roles

**Category roles** (pick exactly one per issue):

- `bug` — something is broken
- `enhancement` — new feature or improvement

**State roles** (pick exactly one per issue):

- `needs-triage` — maintainer needs to evaluate
- `needs-info` — waiting on the reporter for more information
- `ready-for-agent` — fully specified, ready for an AFK agent
- `ready-for-human` — needs human implementation
- `wontfix` — will not be actioned

Every triaged issue must have exactly one category role and one state role.

## State Machine

```
[unlabeled] → needs-triage
needs-triage → needs-info | ready-for-agent | ready-for-human | wontfix
needs-info → needs-triage  (once reporter responds)
```

Unlabeled issues go to `needs-triage` first. From there, move them to one of the terminal states or to `needs-info` if more information is required. Once the reporter responds, move back to `needs-triage` for re-evaluation.

## Invocation

The maintainer invokes the skill and describes what they want in natural language. Interpret and act. Examples:

- "Show me what needs attention"
- "Let's look at #42"
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Showing What Needs Attention

Query the issue tracker and present three buckets, oldest to newest within each:

1. **Unlabeled** — never triaged
2. **`needs-triage`** — evaluation in progress
3. **`needs-info` with reporter activity since last triage notes** — needs re-evaluation

Show counts and a one-line summary per issue.

## Triaging a Specific Issue

### 1. Gather context

Read the full issue: body, comments, labels, reporter, dates. Parse any previous triage notes so you don't re-ask already-resolved questions. Explore the codebase using the domain glossary (`CONTEXT.md`) if it exists, and respect ADRs in the relevant area.

### 2. Recommend

Tell the maintainer the recommended category and state with reasoning, plus a summary of relevant codebase context. Wait for direction before proceeding.

### 3. Reproduce (bugs only)

Before any grilling, attempt reproduction. Report what happened:

- Successful repro with code path identified
- Failed repro (explain what was tried)
- Insufficient detail to reproduce — strong signal for `needs-info`

### 4. Grill (if needed)

If the issue needs more specification, enter grilling mode — ask one question at a time, as in the `brainstorming` skill. Do not ask about things already resolved in prior triage notes.

### 5. Apply the outcome

- **`ready-for-agent`** — post an agent brief comment (see format below)
- **`ready-for-human`** — same structure as agent brief, but note why it cannot be delegated (judgment calls, external access, design decisions, manual testing)
- **`needs-info`** — post triage notes with the specific questions being asked
- **`wontfix` (bug)** — post a polite explanation and close the issue
- **`wontfix` (enhancement)** — save to `.out-of-scope/<slug>.md` with context, decision, and consequences; link it from a comment; close the issue

Apply the appropriate labels after posting.

## Agent Brief Format

```markdown
> *This was generated by AI during triage.*

## What to build

Concise description of the vertical slice. Describe the end-to-end behavior, not the implementation by layer.

## Acceptance criteria

- [ ] Criterion 1
- [ ] Criterion 2

## Blocked by

- Reference to blocking ticket (if any)

Or "None - can start immediately"
```

Keep acceptance criteria measurable and unambiguous. Each criterion should be something an agent can verify independently.
